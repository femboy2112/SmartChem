## Part 1 — Audit integration: the smell, corrected on evidence

**The smell is real.** Two hand-maintained enumerations duplicate the 9-entry
`_DESCRIPTORS` registry (`runtime_registry.py`) with no shared enforcement that they
stay complete:

- `_observable_payload_error` — 9 `if plan.executor_id == …` branches
  (`program.py:1595–1929`).
- `structure_attachment_for_subject` — 2 branches (`structure_ir.py:517,524`).

This is exactly the "a check derived by hand-copying its subject" pattern the project's
own doctrine distrusts (`THE_COMPILER.md:317`).

**But the catastrophe the audit feared does not hold.** The audit worried a tenth
executor "could pass registry validation while silently lacking a payload-error branch,"
and flagged that the fallback past `program.py:1930` was *not verified*. It is now.
`_observable_payload_error` falls through to
`return f"no observable payload validator for executor {plan.executor_id!r}"`
(`program.py:1930`), and its sole caller does
`if payload_error is not None: return self.invalid(...)` (`program.py:2168–2169`). So an
unbranched executor is **refused at completion**, not silently shipped. The
`structure_ir` chain likewise falls through to a benign `NOT_APPLICABLE`
(`structure_ir.py:531–539`).

- **Label:** *Observed* (static read of both the fallback and its caller on the real
  completion path). A synthetic tenth-executor test would upgrade this to *Verified*.
- **Boundary:** this establishes fail-*closed* for the **payload** chain only. The
  **structure-attachment** chain fails *degraded* — a new executor whose subject
  genuinely should carry S0 structure but lacks a branch gets a silent `NOT_APPLICABLE`
  (a missing annotation, never a wrong scientific result). Softer hazard, still worth
  the same guard.

**Workflow rule adopted (spec now, implement on go):** a registry-completeness guard —
a test that **derives** the handled-executor set from `_DESCRIPTORS` and asserts
`_observable_payload_error` and `structure_attachment_for_subject` each cover it, rather
than re-listing it by hand. This is the doctrine applied reflexively: the check must be
derived from the registry it guards, not hand-copied from it. It converts the current
"benign because fail-closed" into "impossible by construction." Any future executor
addition (the multi-file hand-wiring of `FINEMAN…` I.4) must land with this guard green.

## Part 2 — The new capability: probe-evidence contract auditor (proposal)

**One line:** SmartChem already enforces, in *code*, the discipline whose *absence*
caused a retraction on the fine-man side last session ("a check derived from its own
subject checks nothing"). The auditor lets SmartChem's discipline check fine-man's
numerical probes for epistemic hygiene — teeth, provenance-independence, source-locks,
tier boundary — **without** claiming to verify the physics and **without** entering the
closed registry.

- **Shape:** a new `smartchem.evidence` subpackage + a thin `smartchem verify-probes`
  CLI, reusing `contracts.py` primitives (`ClaimKind` ⊥ `EvidenceStatus` at
  `contracts.py:46–101`; `canonical_digest` at `contracts.py:108–191`). Decoupled Mode B
  (JSON manifest contract) is primary; neither repo imports the other.
- **The five rules** each transplant one existing SmartChem discipline
  (`FINEMAN_VERIFICATION_BRIDGE_2026-08-06.md` III.3): teeth (⇐ DERIVED-MENU LAW),
  provenance-independence (⇐ independent-verifier / no shared code),
  source-lock (⇐ refusal over unearned answer), scope (⇐ casualty lists),
  tier-boundary (⇐ `ClaimKind` ⊥ `EvidenceStatus`).

**Authority boundary — the collision to hold the line on.** This tool sits *outside* the
registry+approval+independent-verifier seam that gives everything else in this repo its
scientific authority. That is a structural first for SmartChem. Two guards keep it honest:

1. **Diagnostic-only, external-only.** Its output certifies *epistemic hygiene of a probe
   suite*, never the correctness of physics, and never SmartChem scientific authority. A
   loud banner rides on every certificate
   (`FINEMAN_VERIFICATION_BRIDGE_2026-08-06.md` III.4). If its output is ever wired back
   into SmartChem's *own* claim ledger, that is a new decision requiring its own gate —
   not a silent extension.
2. **No label-borrowing (new constraint, this checkpoint).** Because it reuses
   `contracts.py`'s authority-bearing vocabulary (`EvidenceStatus`, the
   `ANALOGUE/STRUCTURAL_TOY` tier) in a context where our approval/verifier machinery does
   **not** run, the tool must never let a reused label *imply* the governance it carries
   in-repo. It never upgrades `EvidenceStatus` past `structural-toy`, and B0 must document
   that these labels are being used descriptively, not as certificates of the SmartChem
   seam. This is the subtler leak underneath the banner and it is a B0 acceptance item.

**Why it's a fit, not a forced marriage:** it's philosophically the same animal as the
`EvidenceIR` layer already carved out as a separate concern in the category backbone
roadmap — claim scope / evidence status / casualties / falsifiers, kept apart from any
solver result — just externalized to an untrusted sibling repo.

## Part 4 — Standing rules delta

Adds to the existing continuation rules (`ROADMAP_2026-07-27.md` "Continuation rules"),
does not replace them.

- **New workflow rule (registry completeness):** any enumeration that shadows the closed
  registry (`_observable_payload_error`, `structure_attachment_for_subject`, and any
  future sibling) must be **guarded by a test that derives its expected set from
  `_DESCRIPTORS`**, never by a hand-maintained parallel list. Adding an executor requires
  that guard green.
- **New capability boundary (external audit):** a capability that audits an *external*
  repo is diagnostic-only, claims no SmartChem scientific authority, prints its
  hygiene-not-physics banner, and never lets a reused `contracts.py` label imply the
  governance seam it lacks. Feeding any such output back into SmartChem's own ledger is a
  fresh, separately-gated decision.
- **Unchanged and reaffirmed:** the closed, hand-registered nine-executor registry; no
  third-party executor inherits authority by registration; refusal over a
  plausible-but-unearned answer; casualty/omission lists on every certificate.

### Orthogonal-probe phase — the adversarial-hardening result

Two **blind** probes — an adversary reading the code, and a reusability author reading only the
docs — **converged on the same defect**: rules keyed off a field the manifest author controls.
Six bypasses, one disease (*the auditor audited the labels an author volunteers, not the thing
the labels describe*).

- **Closed structurally:** role-laundering (`agreement`/`discriminator`/`pairs_with` are now
  CLAIM-only, fail-closed at construction); the `agreement`-flag common-mode dodge (rule 2 now
  fires on the structural single-bearing-over-report condition, not the self-declared flag);
  toy-discriminator tier promotion (a discriminator must carry above-toy evidence).
- **Documented boundary** (irreducible for a *declarative* auditor; on every certificate banner):
  source-token aliasing, `numeric_result` smuggling, Mode-B rubber-stamp mutations. Each is
  pinned by a regression test so a future tightening is deliberate.
